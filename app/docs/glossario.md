# Glossário da plataforma

Os termos que aparecem no código, nos docs e no Track, com o que cada um é e o que faz. Quando um termo tem um alvo diferente do estado de hoje, a linha diz os dois e aponta o débito (`tech-debt.md`) ou a decisão (`decisions.md`).

## Quem participa

| Termo                      | O que é                                                                                                                                                                                                                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Issuer (emissor)**       | Cliente da Vesta que verifica pessoas e emite credenciais. Tem API key, usuários de backoffice e uma wallet organizacional. **Emissor técnico** faz o KYC (documento, selfie); **emissor comercial** origina o usuário sem fazer o KYC. Hoje existe um cliente em produção |
| **Titular (holder)**       | A pessoa verificada. Guarda a credencial no próprio device e a apresenta quando outra plataforma pede                                                                                                                                                                      |
| **Verifier (verificador)** | Quem precisa saber se a pessoa é verificada sem refazer o KYC: o próprio issuer num novo acesso ou outro parceiro da rede. Pede uma prova, não os dados                                                                                                                    |
| **Vesta**                  | Emite e assina as credenciais, guarda o mínimo para dedup e revogação, gera ou verifica provas e grava o resultado na chain. O alvo é nunca ver PII (TD-018)                                                                                                               |
| **Privy**                  | Custodiante das chaves Stellar: cria a wallet do titular e a do issuer e assina no browser. A Vesta não tem as chaves                                                                                                                                                      |
| **Backoffice**             | Painel do issuer: API keys, credenciais, verificações, wallet e payouts. Autenticado por JWT (`BACKOFFICE_JWT_SECRET`)                                                                                                                                                     |
| **Admin**                  | Operação interna da Vesta (`/admin`), autenticada por `ADMIN_SECRET`: cria issuers, wallets, verifiers                                                                                                                                                                     |

## Credencial

| Termo                                               | O que é                                                                                                                                                                                                                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **KYC**                                             | A verificação de identidade que o emissor técnico faz. Produz CPF, nome, data de nascimento e um nível (`kyc_level`). A Vesta não faz KYC                                                                                                                                          |
| **VC (Verifiable Credential)**                      | Documento JSON assinado pela Vesta que diz "a pessoa com estes hashes tem KYC de nível N, emitido pelo issuer X". Não contém CPF, nome nem data em claro; contém os hashes deles. Segue o modelo de dados de VC do W3C                                                             |
| **`vcHash`**                                        | SHA-256 da VC. É o identificador da credencial em todo lugar: banco, passkey, attestation on-chain                                                                                                                                                                                 |
| **`subjectDid` / `issuerDid`**                      | Identificadores do titular e do issuer dentro da VC. Hoje o `subjectDid` é um UUID aleatório por credencial, o que faz cada credencial ter uma wallet própria (D12)                                                                                                                |
| **`cpf_hash`, `birth_date_hash`, `full_name_hash`** | Poseidon do CPF, da data e do nome normalizado. Ficam na VC e são os sinais públicos do circuito. Hoje sem salt, o que permite força bruta do CPF a partir da chain; o alvo é um commitment com salt (TD-010, decisão de 2026-09-29)                                               |
| **Commitment**                                      | Alvo do `cpf_hash`: `Poseidon(cpf, salt)`. Compromete a credencial com o CPF sem que o CPF possa ser descoberto, porque o salt tem 256 bits                                                                                                                                        |
| **Salt**                                            | Valor aleatório por credencial, gerado na emissão e guardado só com o titular, dentro da VC. Sem ele o commitment não abre                                                                                                                                                         |
| **`cpfDedupKey`**                                   | `HMAC-SHA256(cpf, CPF_HMAC_SECRET)`, guardado no banco. Responde "este CPF já tem credencial?" (`kyc-status`, reuso entre issuers) sem guardar o CPF. A chave não rotaciona (risco aceito, SUB-010). O alvo distante é um OPRF, em que a Vesta calcula o mesmo valor sem ver o CPF |
| **`vc_document`**                                   | Cópia da VC inteira que o backend guarda hoje para a recuperação por passkey. Sai no alvo, porque guardaria o salt (TD-018)                                                                                                                                                        |
| **Revogação**                                       | Issuer marca a credencial como `REVOKED` pelo `vcHash`; ela deixa de provar. Só o issuer dono pode revogar (CRED-011)                                                                                                                                                              |
| **Reemissão**                                       | O issuer emite uma VC nova para a mesma pessoa (salt novo, `vcHash` novo) e a antiga é revogada. É o caminho de recuperação no alvo e o de migração para o circuito v2                                                                                                             |

## Passkey e wallet

| Termo                                  | O que é                                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Passkey**                            | Credencial WebAuthn criada no device do titular (biometria ou PIN) e vinculada ao `vcHash` em `passkey_credentials`. Prova que quem está no device é quem registrou a credencial      |
| **Challenge**                          | Valor aleatório emitido pelo backend que a passkey assina. Impede reuso de uma assinatura antiga (anti-replay)                                                                        |
| **Counter (signCount)**                | Contador que o autenticador incrementa a cada assinatura. Se vier menor que o guardado, a passkey pode ter sido clonada (PASS-004)                                                    |
| **Wallet do titular**                  | Conta Stellar criada na Privy para a credencial. Assina a transação da attestation. Hoje nasce na emissão, financiada pelo deployer; o alvo é nascer no browser, patrocinada (TD-011) |
| **Wallet organizacional**              | Conta Stellar do issuer (`organization_wallets`), usada para receber payouts. Ativada no backoffice com prova de controle e trustline                                                 |
| **Prova de controle**                  | O issuer assina um challenge com a wallet no browser; o backend confere com `Keypair.verify`. Mostra que ele controla aquela conta                                                    |
| **Trustline**                          | Autorização da conta Stellar para receber um ativo (o do payout). Reserva patrocinada pela Vesta                                                                                      |
| **Sponsor (patrocínio)**               | Mecanismo Stellar em que outra conta paga a reserva de um item (conta, trustline) sem doar XLM. Hoje só a trustline é patrocinada                                                     |
| **Fee bump**                           | Transação que embrulha outra e paga a taxa por ela. A Vesta usa na attestation para a wallet do titular não precisar de XLM                                                           |
| **Deployer (`VESTA_DEPLOYER_SECRET`)** | Conta da Vesta que hoje faz tudo: admin dos contratos, deploy, patrocínio e fee bump. O alvo separa a chave administrativa (fria) da operacional (quente) (TD-013)                    |

## Prova de conhecimento zero

| Termo                         | O que é                                                                                                                                                                                                                                   |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ZK (zero knowledge)**       | Provar que uma afirmação é verdadeira sem revelar os dados que a tornam verdadeira. Aqui: "tenho KYC de nível ≥ N na credencial X" sem mostrar CPF, nome ou data                                                                          |
| **Circuito (`vesta_kyc`)**    | O "livro de regras" da prova, escrito em circom. Recebe entradas privadas (CPF, data, nome, nível) e públicas (hashes, nível mínimo) e impõe: os hashes batem e o nível é suficiente. O fonte se perdeu; só os artefatos existem (TD-010) |
| **Sinal privado / público**   | Entrada que só o provador conhece / entrada que o verificador também vê. Os sinais públicos vão para a chain nos `pub_signals`. Hoje: `cpf_hash`, `birth_date_hash`, `full_name_hash`, `min_kyc_level`, `kyc_ok`                          |
| **Restrição (constraint)**    | Uma equação que o circuito impõe. Um circuito **sub-restrito** calcula o valor certo mas não obriga a ele: dá para gerar prova válida de algo falso. É a classe de bug número um em ZK                                                    |
| **Range check**               | Restrição que garante que um número cabe em `n` bits antes de compará-lo. Sem isso o comparador "dá a volta", como um relógio                                                                                                             |
| **Witness**                   | Todos os valores intermediários do circuito para uma entrada concreta. O `wasm` calcula o witness; a prova é gerada a partir dele                                                                                                         |
| **Groth16**                   | O sistema de prova usado. Prova pequena (uns 200 bytes), verificação rápida e barata on-chain; exige cerimônia por circuito                                                                                                               |
| **BN254**                     | A curva elíptica usada. É a que o Soroban sabe verificar nativamente (`bn254().pairing_check`)                                                                                                                                            |
| **Poseidon**                  | Função de hash desenhada para ser barata dentro de circuitos. Usada nos hashes da VC (`vc.service.ts`) e no circuito                                                                                                                      |
| **wasm**                      | O circuito compilado; calcula o witness. Fica em `zk-artifacts/`                                                                                                                                                                          |
| **zkey (proving key)**        | Chave para gerar provas deste circuito, resultado da cerimônia. Pública, uns 600 KB, versionada no git                                                                                                                                    |
| **VK (verification key)**     | Chave para verificar provas deste circuito. Pequena e pública. Hoje é passada por chamada ao contrato; o alvo é ficar gravada nele (TD-012)                                                                                               |
| **ptau (powers of tau)**      | Fase 1 da cerimônia, genérica para qualquer circuito até um tamanho. Reaproveita-se um arquivo público, baixado com checksum                                                                                                              |
| **Cerimônia (trusted setup)** | Processo que gera a zkey e a VK. Cada participante contribui aleatoriedade e destrói o que usou ("toxic waste"); basta um honesto para o sistema ser seguro. Mudar o circuito exige cerimônia nova                                        |
| **Prova (proof)**             | Os bytes que convencem quem tem a VK de que o livro de regras foi satisfeito para aqueles sinais públicos                                                                                                                                 |
| **Nullifier**                 | Alvo (TD-017): `Poseidon(salt, scope)` como sinal público. Identifica a credencial só dentro de um escopo, impede provar duas vezes no mesmo escopo e evita que verifiers correlacionem a mesma pessoa                                    |
| **Scope e nonce**             | Alvo (TD-017): sinais públicos que amarram a prova a um verifier ou ação (`scope`) e a uma sessão (`nonce`). Sem eles a mesma prova vale em qualquer contexto                                                                             |
| **Proving no cliente**        | Alvo (TD-018): gerar a prova no browser com snarkjs, de modo que CPF e salt nunca saiam do device. Hoje a prova é gerada no servidor (`zk.worker.ts`)                                                                                     |
| **OPRF**                      | Função pseudoaleatória "cega": o cliente esconde a entrada, o servidor aplica a chave secreta sem ver a entrada, o cliente remove a cegueira. Permite a Vesta calcular o `cpfDedupKey` sem ver o CPF. Padrão RFC 9497                     |

## Chain

| Termo                              | O que é                                                                                                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Soroban**                        | A plataforma de contratos inteligentes da Stellar. Contratos em Rust compilados para wasm                                                                    |
| **`vesta-verifier`**               | Contrato que verifica a prova Groth16 e grava a attestation. Hoje aceita qualquer VK e qualquer chamador (TD-012)                                            |
| **Attestation**                    | Registro on-chain "a credencial `vc_hash` foi provada válida em T". Sem PII. É o que um terceiro consulta para confiar numa credencial sem falar com a Vesta |
| **`vesta-issuer-registry`**        | Contrato que mapeia o DID do issuer para o participante (técnico ou comercial, status). Resolve "quem emitiu esta attestation"                               |
| **`vesta-payout-vault`**           | Contrato que guarda créditos de comissão e liquida payouts. Fora do caminho crítico por ora (TD-015)                                                         |
| **DID (`did:stellar`, `did:key`)** | Identificador descentralizado. O issuer usa `did:stellar`, ligado à conta Stellar; o titular hoje recebe um `did:key` que não é um did:key de verdade (D12)  |
| **`require_auth`**                 | Instrução Soroban que exige a assinatura de um endereço para a função rodar. Falta no `verify_proof` (TD-012)                                                |
| **TTL de storage**                 | No Soroban, dados persistentes expiram se ninguém renovar (`extend_ttl`). A attestation precisa de renovação (TD-012)                                        |
| **Evento (on-chain)**              | Registro que o contrato publica (`proof_verified`) e que um indexador pode ler. É a fonte de verdade natural para uma arquitetura orientada a eventos        |
| **Testnet / mainnet**              | Rede de testes, com XLM sem valor, e rede real. Staging usa testnet                                                                                          |

## Backend

| Termo                   | O que é                                                                                                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API key**             | Credencial do issuer para `/public`. Guardada como hash com prefixo visível; rotação com 30 dias de convivência (`api-key-rotation.md`)                          |
| **Tenant / isolamento** | Cada issuer só vê e mexe no que é dele. Recurso de outro issuer responde 404, nunca 403, para não vazar existência                                               |
| **Evento de domínio**   | Fato do negócio (`CredentialIssued`, `ProofVerified`) publicado depois do commit para outros módulos reagirem. Hoje em processo, sem outbox (TD-001)             |
| **Outbox**              | Tabela em que o evento é gravado na mesma transação do dado; um worker publica depois, com retry. Garante que nenhum efeito se perde se o processo cair (TD-001) |
| **Indexer**             | Worker que lê os eventos da chain e projeta no Postgres. Torna a chain a fonte de verdade em vez do que o backend "acha" que aconteceu                           |
| **ChainPort**           | Interface agnóstica de rede (prova, recibo, endereço) com um adapter Stellar. Baixa prioridade desde a weekly de 29/09 (TD-002)                                  |
| **Ledger de comissão**  | `commission_ledger_entries`: o que cada parceiro tem a receber por verificação, com período de segurança. Fora do caminho crítico (TD-015)                       |
| **Mock mode**           | `ZK_MOCK_MODE` e `STELLAR_*` de placeholder: local e testes rodam sem chain e sem prova real. Fora de local o boot falha sem os artefatos (SEC-005)              |
